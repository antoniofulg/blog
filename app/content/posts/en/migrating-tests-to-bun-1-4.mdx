My normal development session is not one editor and one terminal. I often have several worktrees open, each with its own dependencies, dev server, type checker, and test process. One feature may be running integration tests while another is installing packages and a third is building the application.

That setup exposed a cost I barely noticed when I worked in one tree at a time. The laptop would stall. A test that passed alone would time out inside the full suite. Fans and memory pressure became part of the feedback loop. Instead of continuing with a feature, I would wait, rerun the command, and then decide whether the failure belonged to the code or to a machine already doing too much.

I did not measure feature lead time, so I will not invent a productivity percentage. What I did measure was the part underneath that experience: how long each command occupied the machine, how much resident memory its process tree reached, and whether it executed the same tests as the reference.

Bun 1.4 improved that queue. It did not win every comparison, and the places where it lost were useful because they defined the setup I kept.

## Measuring occupancy changed the decision

Peak memory matters when several worktrees run together, but it is only half of the problem. A process that peaks slightly higher and exits much sooner may block the next job for less time. That is why I recorded both peak RSS and RSS x wall time as an approximation of memory occupancy.

The distinction changed the decision. Native Bun Test used 3.24% more peak RSS than Bun-hosted Vitest in the selected two-worker profile. If I had looked only at the peak, Vitest would have won. Bun Test finished 21.64% sooner, so its RSS x time was 19.10% lower. For a serialized local queue, releasing memory sooner was the more useful result.

The same rule applied to every experiment:

1. Both arms had to execute the same inventory and produce the same outcomes.
2. Each controlled profile discarded a warm-up and retained five interleaved samples.
3. Memory included the process tree, not only the coordinator process.
4. Contaminated samples stayed in the report but could not produce a winner.
5. Browser comparisons had to state whether the engine and lifecycle matched.

Those rules invalidated several attractive early numbers. That was annoying, but less annoying than publishing a fast result that came from running less work.

## The measurements produced a mixed setup

This is the final decision matrix. Each row answers a different question.

| Boundary | Compared workload | Winner on this machine | Adopted result |
| --- | --- | --- | --- |
| Dependency installation | Two retained steady-state local samples | Bun 1.4 | `bun install --frozen-lockfile` |
| Unit, component, and integration runner | 113 matched product files, isolated-2 | Native Bun Test | Bun Test with two isolated workers |
| Complete Chromium E2E runtime | 49 Playwright tests, five measured samples | Bun-hosted Playwright | Playwright executed through Bun |
| Lightweight macOS browser smoke | The same five public routes, cross-engine | Bun.WebView WebKit | Optional local smoke only |
| Chromium driver | The same five public routes and Chromium executable | Playwright Page | Keep Playwright for the complete E2E suite |

This table is deliberately not a single ranking. Bun Test and Playwright solve different layers. WebView WebKit won a five-route smoke, not the 49-test suite.

## Bun made dependency installation a non-event

I compared `npm ci` on Node 24 with `bun install --frozen-lockfile` on Bun 1.4. I removed `node_modules` before each measured run and discarded the first run as cache warm-up. Only two steady-state samples remained, so this is a small observation from one Apple M3 Pro, not a general package-manager benchmark.

| Steady-state median | npm / Node 24 | Bun 1.4 |
| --- | ---: | ---: |
| Time | 8.7 s | 1.9 s |
| Peak RSS | 1,095 MB | 57 MB |

The practical change was obvious. Starting a new worktree no longer meant giving one package installation more than a gigabyte of resident memory while other trees were already active. The [committed installation report](https://github.com/antoniofulg/blog/blob/main/docs/benchmarks/node-vs-bun/README.md) preserves the retained samples and the excluded warm-up.

## Bun Test shortened the local queue

My first Bun Test comparison said the opposite. Bun Test looked roughly twice as slow as Vitest. That experiment mixed inventories, DOM setup, isolation, timeouts, and worker counts. It measured the migration gaps along with the runner.

The revalidation started again with independent Vitest-first and Bun-first suites. The matched product cohort contained 113 files, 2,057 passing tests, and 84 normalized environmental skips. Every finalist retained five valid samples.

| Selected isolated-2 profile | Bun-hosted Vitest | Native Bun Test |
| --- | ---: | ---: |
| Median wall time | 33.080 s | 25.922 s |
| Measured range | 32.590-34.450 s | 24.048-31.311 s |
| Peak RSS | 2,751.9 MiB | 2,841.1 MiB |
| RSS x time change | baseline | 19.10% lower |

The peak increased by 89.2 MiB, but the process released it 7.158 seconds earlier at the median. That trade-off fits my worktree queue better than optimizing only the highest instantaneous number.

It was not a universal Bun win. At four isolated workers, Vitest was 4.33% faster. Bun's own [parallel test documentation](https://bun.com/docs/test/parallel) explains why worker processes and per-file isolation have costs as well as benefits. The repository now uses `--parallel=2 --isolate`, the profile supported by its own measurements rather than by the largest worker count available.

After the cutover, I ported the active infrastructure tests and removed Vitest, jsdom, and the duplicate comparison tree. The current local gate runs 2,374 tests across 134 files: 2,273 pass, 101 are environment-gated, and none fail. The [runner-first report](https://github.com/antoniofulg/blog/blob/main/docs/benchmarks/bun-test-revalidation/README.md) contains the complete matrix and raw runs.

## Bun shortened the complete Playwright run too

I kept Playwright as the E2E runner and changed only the runtime hosting it. Both arms used the same application server, Chromium project, one worker, zero retries, and all 49 tests. Each arm had one warm-up plus five interleaved measured samples.

| Median across five samples | Node 24 + Playwright | Bun 1.4 + Playwright |
| --- | ---: | ---: |
| Duration | 12.998 s | 11.356 s |
| Peak RSS | 796.6 MiB | 361.5 MiB |
| Outcomes | 49 / 49 | 49 / 49 |

Bun-hosted Playwright was 12.63% faster and used 54.62% less peak RSS. Including warm-up, its total wall time was 17.39% lower. This comparison matters more to the daily setup than a browser microbenchmark because it preserved the complete E2E contract.

The result still belongs to this host and this suite. It is not a promise that every Playwright project becomes 12.63% faster under Bun. The [runtime report](https://github.com/antoniofulg/blog/blob/main/docs/benchmarks/e2e-runtimes/runtimes-2026-08-23T08-20-02-241Z.md) records the five samples, machine load, runtime versions, and 49/49 outcomes. Node remains available through `test:e2e:node` if the Bun-hosted path regresses.

## WebKit won five smokes, not the E2E suite

This boundary caused the most confusion, so I ran a second experiment. Playwright Test remained the harness for declarations, assertions, hooks, timeouts, and reports. A custom fixture selected one of three drivers:

- Playwright Page with Chromium.
- Bun.WebView with the macOS WebKit backend.
- Bun.WebView with the same Chromium executable used by Playwright.

None of the WebView projects requested Playwright's `page`, `browser`, or `context` fixtures. All three executed the same five anonymous public routes. The complete 49-test suite was not part of this benchmark.

| Driver under Playwright Test | Cold wall | Warm wall | Cold peak RSS | Warm peak RSS |
| --- | ---: | ---: | ---: | ---: |
| Playwright Page + Chromium | 2,639.59 ms | 4,248.58 ms | 932.7 MiB | 875.4 MiB |
| Bun.WebView + WebKit | 1,729.43 ms | 2,255.52 ms | 316.3 MiB | 302.0 MiB |
| Bun.WebView + same Chromium | 4,290.78 ms | 6,035.99 ms | 994.7 MiB | 992.7 MiB |

WebKit won the operational five-smoke comparison: 34.48% faster cold, 46.91% faster warm, and about 66% less peak RSS. But this is cross-engine evidence. Bun's [WebView documentation](https://bun.com/docs/runtime/webview) says the experimental macOS backend uses the system `WKWebView`; Playwright Page used Chromium here.

The same-engine control went the other way. Bun.WebView Chrome was 62.56% slower cold and 42.07% slower warm than Playwright Page. Putting WebView below the Playwright Test harness did not remove the dominant Chrome automation cost.

I kept WebKit as an optional local five-route smoke because that is the boundary it won. Playwright still owns authentication fixtures, `storageState`, semantic locators with auto-waiting, traces, permissions, request inspection, and Chromium/Firefox/WebKit projects. Those capabilities are why the [complete Playwright suite](https://playwright.dev/docs/browsers) remains the release signal. The [matched-harness report](https://github.com/antoniofulg/blog/blob/main/docs/benchmarks/playwright-webview-hybrid/README.md) contains all 36 valid samples and both warm-up layers.

## Faster tools exposed lifecycle bugs

The final validation exposed another part of the multi-worktree problem. Several integration setups had inherited Bun Test's five-second default timeout even though they booted PGLite, applied a schema, compiled MDX, initialized Shiki, or started Better Auth. Under contention, these tests crossed their budget and failed even when their assertions were correct.

The fix was not to weaken assertions or add retries. Slow lifecycle hooks received explicit 30- or 60-second budgets, and database cleanup moved into `finally` where needed. A memory measurement also switched from a repeated byte pattern to random data so macOS memory compression could not erase the resident-memory signal.

These were suite bugs, not proof that Bun was unstable. A faster runner shortened the pressure window, but realistic setup budgets and deterministic allocations made the result trustworthy. That distinction matters when a failure blocks feature work: I need to know whether the product broke or the test harness ran out of assumptions.

## I kept the winner at each boundary

| Layer | Current choice |
| --- | --- |
| Installation and scripts | Bun 1.4 |
| Unit, component, integration, and infrastructure tests | Native Bun Test, two isolated workers |
| Complete E2E | Playwright Test hosted by Bun, one worker |
| Cross-browser coverage | Playwright Chromium, Firefox, and WebKit projects |
| Browser fallback | Node 24 + Playwright |
| Fast local public smoke | Optional Bun.WebView WebKit, five routes |

The improvement is not one dramatic command. Installs stop monopolizing memory. The main test suite releases memory sooner. The complete E2E run peaks 435.1 MiB lower. When I only need a quick public-route signal on macOS, the five-smoke WebKit path is available without pretending it replaced Playwright.

That makes multiple worktrees easier to schedule. One tree finishes and gets out of the way sooner, leaving the machine available for the next feature instead of turning every test run into a negotiation for memory.

## What I would do differently

I would lock the test inventory before measuring anything. The first apparently fast Bun arm had failed to load 32 files; fewer files are not an optimization. I would also separate lifecycle comparisons before the first WebView run. A warm persistent WebKit session and a cold Playwright browser answer different questions even when they visit the same routes.

Finally, I would reserve a quiet measurement window earlier. The harness correctly rejected contaminated samples, but explaining invalid rows took longer than rerunning them would have on an idle machine.

## Where the setup stands on 2026-08-25

The migration is complete locally. Bun 1.4 owns installs and native tests. Playwright still owns the complete browser suite, now hosted by Bun, with Node as fallback. Bun.WebView WebKit remains a small local optimization for five public smokes.

GitHub Actions was unavailable during the final cutover because the account had no credits, so the final evidence comes from repeated local gates and committed raw reports. The next useful measurement is not another synthetic race. It is observing flakiness and memory occupancy when several real worktrees queue work over the coming weeks.
